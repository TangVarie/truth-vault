# 2026-11-14 审查修复部署说明

本批变更只备好代码、迁移和本地测试。没有对生产执行 SQL、调用付费接口或手动触发 Actions。

## 部署顺序

1. 负责人先在目标 Supabase 应用 `schemas/notes_v1_25_sync_runs.sql`，再应用 `schemas/notes_v1_26_feature_failure_recovery.sql`。均可重跑；两份迁移只涉及状态和既有答案的恢复，不调用模型。
2. 确认两份迁移成功后，部署本分支代码。没有 v1.25 时采集在业务行写入前报出迁移文件名并拒绝继续；没有 v1.26 时特征恢复能力也必须明确失败，不能按旧逻辑照绿。
3. 保持原有定时安排，观察下一次正常周期，不需要为了部署单独回填。检查各项目 `Done.scan_completed`、新账本 `completed_at/seen_count` 和模型答案有效率、失败队列计数。
4. 本批另有收紧 public 业务表 authenticated 广读的独立安全迁移，见该文件头与相应 PR 说明；不要把它与匿名聚合看板授权混为一谈。

## 完整扫描账本（F04）

`note_sync_runs.run_seq` 在抓飞书之前分配。只有未限量、全部页抓完、既有行均处理成且账号/notes/指标写入成功，才调用 `complete_note_sync`。完整返回 0 行同样提交完成。失败、进程中断、限量扫描只留下未完成 run，消费者忽略它们。

完成 RPC 在一个数据库事务里更新成员证据和完成记录。`note_sync_presence` 每篇只保留最近一次成功扫描的序号，写入取 `greatest`；视图只选最大已完成序号，因此旧 run 晚完成、或两个完成操作重叠锁等待，都不能回退最新快照。该规则不依赖机器时钟，也不再把 notes 上可交错覆盖的 `last_seen_*` 当作删帖证据。原有列暂留作历史诊断；采集日志和下游都改读同一张完成视图。

迁移会保存旧视图已知的“见过/已消失”分类作为基线，不替从未见过的笔记编造证据。它无法重建历史上没有记账的空扫描或失败扫描；需要下一次成功全量扫描建立新事实。未完成 run 仅含项目、run id 和时间，不含正文或密钥；按正常调用量每项目每日一行，成员证据不按天复制整份正文。

完成 RPC 的第三个可选参数另记“本轮确实见过、但没处理成的新行 ID”。成功成员仍必须已经存在且归本项目；失败观测只接受本项目稳定前缀、无空值/重复的 ID。`note_sync_presence` 因此是源记录观测元数据，不是 notes 的子表：保留 project 外键，移除 note 外键，允许证据先于业务行入库。这样较新扫描看见一个坏行时，即使较旧扫描稍后才把它建成笔记，也不会把“见过但写坏了”误判为“源里已删”。既有失败行已在库时仍按 D-058 阻止完成，未改变该取舍。人工彻底清理项目数据时应单独清理其成员元数据；正常 note 删除不再自动抹去源观测证据。

此变化仍然只报告缺席，不删除 note、已推的样本或经验卡。源表本身在抓取期间变化时，飞书分页仍不是事务快照；本次解决的是完成状态和并发发布证据，不承诺重写全部业务数据的并发控制。

本地验收：`scripts/check_sync_runs.py` 执行真实 main 的空扫描、部分写失败、限量、后续页失败、dry-run、完成提交失败和恢复；`scripts/check_sync_runs.sql` 验证事务、零成员、未知笔记和旧完成顺序；`scripts/check_sync_runs_concurrent.py` 在两个真实 Postgres 连接中制造行锁等待，确认较旧完成不会覆盖较新快照。

## 回滚

代码与新视图应作为同一功能发布。出现问题时可先暂停采集/特征定时并回滚应用版本，保留账本表用于核对；不要重新应用 v1.21 覆盖 v1.25 视图，也不要删掉成员证据来“清告警”。旧代码仍可能写 notes 的诊断戳，但不会更新新完成账本；长期回退旧代码会使完成快照停止，须明确安排恢复。数据库权限变更如需回滚，应先核现有合法消费者，不能无条件恢复五表广读策略。

## F03：特征失败恢复与旧有效答案保护

**先应用 v1_26，再部署新 worker/使用新脚本。** 新代码遇到缺恢复表或 RPC 会报出迁移文件名称并失败，不回退到旧完成判据。迁移只排队历史全 NULL 模型快照，不删除旧答案，也不调用模型；API 权限只给 service_role。详细语义见 [feature-annotation-recovery.md](feature-annotation-recovery.md)。

真正问过模型、但一篇的全部模型答案无效时，不落答案或完成标记、退出非零。没正文/没标题而没有可问的问题属于真实不适用，不因此隔离；零星 NULL 仍按 D-083 留存。写答案改用数据库单条冲突更新：NULL 不盖旧有效整行，所以保留的旧答案仍显示旧 SHA/时间，不伪装成本轮测得。

每个主体/题库SHA/抽取器/run_tag 先原子预留尝试：首次失败至少24小时后重试，第二次失败再等48小时，第三次失败隔离。崩溃同样消耗预留。自动并发不能重复认领；独立尝试令牌阻止旧请求清掉新请求的失败状态。`Done` 增加 `groups_invalid`、`model_valid_rate`、`model_no_valid`、`retry_deferred`、`retry_quarantined`；还有待退避/隔离项时不称完成，脚本非零。统计脚本仍把这些篇计作未解决，工作流无进展时停止探测，重复探测不继续付模型费。

修好模型/网关并获得相应模型调用授权后，用现有 backfill 或脚本对点名篇执行一轮 `--reannotate --note-ids NOTE_ID --limit 1` 显式恢复；不要在部署中自动重放。失败仍保留隔离，成功才清队列。新的模型/题库快照拥有独立预算。可只读查询失败队列的 ID/尝试次数/错误类型，不需要客户原文。

本地回归入口：`python scripts/check_feature_failure_recovery.py`（真实 main 双轮及三次封顶、显式恢复、历史标记、缺迁移拒跑）；`scripts/check_feature_failure_recovery.sql`（PostgreSQL 原子预留、令牌、有效答案和权限，合成夹具回滚）。回滚代码时应暂停特征夜跑后再回旧 worker，保留 v1_26 的队列/函数供排查；旧代码不认识恢复队列，恢复旧夜跑会重新引入原缺陷。

## 失败队列与健康吞吐

已有退避/隔离项会让单次 worker 返回非零，但不能因此把同项目后面的健康待办长期锁在首批。features-sync 只在回包明确证明“本批健康篇已成功，当前没有新失败，唯一未完成项为历史退避/隔离”时继续扣健康产出的预算。恢复项目在收尾统一判红；只有隔离无健康篇时不再请求模型；本批新增零有效或 API/写入错误仍停止项目，防止继续付费。`scripts/check_feature_batch_loop.py` 直接运行工作流 shell，假 worker 内执行真实 main，覆盖这三种边界。
