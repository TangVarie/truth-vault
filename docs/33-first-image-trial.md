# 首图试跑（I-29，D-157）

2026-11-16。owner 11-16 定的是小的那一版：不补全部 3,514 篇；先试跑，过了再只给经验卡背后的那些帖（今天 45 篇）和每晚的新帖做首图特征。这份文档讲试跑怎么跑、花多少、报告怎么读，以及一件只读查清的事：爆帖的封面能不能从发布链接拿到（第 7 节）。

合并这个 PR 不改任何夜跑，不花钱，不要 owner 跑 SQL，不加环境变量，运营不用做任何事。

## 1. 试跑做什么

1. 只读地从库里取每篇帖的档位、标题和四个附件列，按下面的分层抽样。档位只用来抽样。
2. 用夜跑同步的那组飞书凭证（`FEISHU_APP_ID` / `FEISHU_APP_SECRET`），按 `file_token` 把首图下载到 runner 的内存里，缩成长边 1,024 像素的 JPEG。
3. 让看图的模型答固定的题（`prompts/first_image_questions_v0_1.yaml`，题库 `fi-v0.1`，草案）。模型只看到图，看不到档位、数据、标题、正文。
4. 按试跑之前写死的线，出一份只有计数的报告。

试跑不写库：答案只在内存里，比完就丢。图片不写盘、不进 artifact、不进日志。报告里没有图片、标题、封面上的字、文件名、链接、note_id。

### 样本

| 层 | 多少 | 怎么抽 |
|---|---|---|
| 常规图 | 48 张 | 有带图爆帖的四个项目（TUGE、RIO、OKMAN、HATHERINE），各 6 篇爆（爆或大爆）6 篇趴，JPEG 或 PNG，飞书里已删的不抽 |
| 难办的文件 | 12 个 | 所有项目里抽：HEIC 4 个、20 MiB 以上 4 个、视频 2 个、类型为空的 2 个 |
| 封面检查 | 39 篇 | 有多图帖的 13 张表各 3 篇；只下载、只解图，不调模型 |
| 列检查 | 6 篇 | RIO、TXQ、WTG 各 2 篇，「内容配图」和「笔记截图」的第一个文件各问一题（是不是封面） |

抽样按 `md5(note_id + 固定种子)` 排序，同一份数据每次抽到同一批。首图的取法：`内容配图`、`笔记配图`、`图片` 三列里第一个非空的，取第 0 个附件。

### 题

14 道，都是闭集。12 道模型答，分三组，每组 4 题，一次调用只问一组，组与组不合并（文字题库「一次最多 4 题」的规矩照搬，`docs/28` §5.3）。另外 2 道（封面大字是不是重复标题、有没有数字）由代码从模型抄下来的大字和标题算，所以模型连标题也看不到。

| 轮次 | 模型 | 图 | 调用 |
|---|---|---|---|
| 两轮分组问（a、b） | 中档 Sonnet | 58 张（60 个里 2 个视频不问） | 各 174 |
| 逐题单问 | 中档 | 前 20 张常规图 | 240 |
| 长边 1,568 | 中档 | 前 20 张常规图 | 60 |
| 两轮分组问（a、b） | 便宜档 Haiku | 58 张 | 各 174 |
| 逐题单问 | 便宜档 | 前 20 张常规图 | 240 |
| 列检查 | 中档 | 12 个文件 | 12 |

合计 1,248 次调用。

## 2. 怎么跑

GitHub → Actions → **First image trial (manual · counts-only report)** → Run workflow。只能手动点，没有定时。文件是 `.github/workflows/first-image-trial.yml`，跑的脚本是 `scripts/first_image_trial.py`。

| 输入 | 默认 | 含义 |
|---|---|---|
| `tier` | `both` | `mid` 只跑中档；`cheap` 只跑便宜档；`both` 两档都跑并互相比。要决定用哪一档必须是 `both` |
| `max_images` | `0` | 每一层最多取几个；`0` = 上表的全量。冒烟填 `2` |
| `dry_run` | `true` | `true` 不下载、不调模型、不花钱，只报样本够不够数、要调多少次、纸面上大约多少钱 |

建议顺序：

1. `dry_run=true`：看每一层抽不抽得够。
2. `dry_run=false`、`max_images=2`：冒烟。核两件事：飞书给不给下载、中转站收不收图片。纸面上约 4 元（两档一共 106 次调用：这两张图七轮都要走，逐题单问和大图那两轮也在内）。小样本不会给出「过线」的结论。
3. `dry_run=false`、`max_images=0`：正式试跑。

报告在这次运行的 Summary 页，也在 artifact `first-image-trial-report` 里（`first-image-trial.md` 和同名 `.json`，只有计数）。

本地等价的命令（要有同样的环境变量）：`cd scripts && python first_image_trial.py --tier both --dry-run`。

## 3. 花多少，怎么保证不超

- 纸面估算：正式试跑约 43 元，其中中档约 41 元。这是按假设算的：图片 token = 宽 × 高 ÷ 750、中转站倍数 1.8、汇率 7.2，三样都没对过账单。试跑量出来的 token 数才是实数。
- **硬上限写死在代码里**（`scripts/first_image.py`）：3,800,000「输入当量 token」（输入 + 5 × 输出），全按中档价算约 98 元；另有 1,400 次调用的上限。每次调用之前查：已花的加上这一次的预留会越线，这一次就不发，之后也都不发。SDK 自带的重试在试跑里关掉了，所以一次调用就是发出去的一个请求；只有配了备用中转站、主站这一次又失败时，会再打备用站一次（一次调用最多两个请求，主站失败的那个不另记用量）。命令行参数只能把上限调低。
- 中转站回包里没有用量的调用、失败的调用，都按预留的数记账（宁可多算）。
- 第一张图先单独走一遍：飞书不给下载，或者中转站头一次调用连重试都没成，就停，不往下花。模型调用连着失败 6 次也停。
- 另有时间上限 300 分钟（job 上限 330 分钟），到点不再开新图，报告照出。
- 钱只在 `scripts/model_prices.py` 一个文件里算：官方标价（原先在 `mask_external_names.py`，数字没变）、中转站倍数、汇率。后两个标着「假设」，报告里每个「元」都带这个标记。

## 4. 缺什么会怎样

正式跑之前先查，缺了在花钱之前就停，并点名缺的是哪个：`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`ANTHROPIC_API_KEY`（都是夜跑已经在用的 secret），以及 Pillow 和 pillow-heif 两个图片库。这两个库只有这个 workflow 装（`scripts/requirements-first-image.txt`），夜跑装的 `requirements.lock` 没动。

退出码：0 = 跑完或干跑；2 = 开跑前的检查没过，或第一张图就被拒；3 = 中途到了上限，报告只覆盖跑到的部分。

## 5. 报告怎么读

| 节 | 看什么 | 线 |
|---|---|---|
| 1 样本 | 每一层抽到几个 | 不够数的层，下面对应的结论不成立 |
| 2 计划与花费 | 实际调用数、token、约合多少元；每张图平均多少 token；经验卡那 45 篇和每晚新帖大约多少钱 | 元是按假设价估的 |
| 3 下载与解图 | 常规图可用的占比 | ≥ 90% |
| | HEIC、空类型、20 MiB 以上各解开几个；视频记成 `first_is_video`、不调模型 | HEIC 4/4，空类型 2/2，大文件至少 3/4，视频 2/2 |
| | 折算到全量 3,514 篇，用不了的占比 | ≤ 10% |
| 4 列检查 | RIO、TXQ、WTG 的「内容配图」是不是帖子自己的图 | 6 篇全对；不然这三个项目的取列规则先别用 |
| 5 封面检查 | 每张表多图帖的第一个附件下不下得到、解不解得开；`cover_unconfirmed` | 见下 |
| 6 逐题一致率 | 同一档两轮的一致率和 κ；分组问对逐题单问；中档对便宜档 | 一致率 ≥ 0.90 且 κ ≥ 0.60；抄字那一题按匹配规则 ≥ 0.85；分组对单题 ≥ 0.90 |
| 7 验收 | 用哪一档 | 便宜档要在中档留下的每一道题上自己过线，并且和中档对得上；否则用中档 |

几个词：

- **κ**：去掉「碰巧一样」之后的一致程度。
- **`kappa_undefined`**：这道题的答案一边倒（最常见的答案占到 90% 以上），或者 κ 算不出来。这样的题一致率再高也**不算过**，记成「还没验证」，要换一批含少见答案的图再测。
- **对数不够**：两轮都有有效答案的图少于 30 张（20 张的子集少于 15 张），不下结论。冒烟跑的每一题都会是这个。
- **过，但要单独问**：两轮对得上，但分组问和单题问对不上，这道题以后单独一次调用问。
- **`cover_unconfirmed`**：多图的帖，没人确认过「第一个附件就是封面」。试跑不让任何人看到图片，所以它只核第一个附件下得到、解得开；每张表都带这个标记。带着这个标记的多图帖以后不上经验卡、不进封面建议。某张表的运营确认了习惯之后，把项目名加进题库文件的 `cover_confirmed_projects`。

## 7. 只读查清的一件事：爆帖的封面能不能从发布链接拿到

背景：426 篇爆帖里 309 篇没有首图（NUC、NRT_2、NRT_3、SPX 的爆帖一篇都没有），它们都有发布链接。问题是：用系统已经在付费的东西，能不能把这些封面拿回来。查的是 linkcheck 仓（`xhsearch/`），11-16 只读，没有调任何接口。

| 问题 | 答案 | 依据 |
|---|---|---|
| linkcheck 现在每轮付费调的是什么 | 小红书只调评论接口。详情接口默认不调（`detail_within_days` 默认 0，因为它只为已经去掉的点赞、收藏列存在，占过月成本的 39%） | 代码：`xhsearch/config.py`、`xhsearch/providers.py` |
| 评论接口的回包里有没有帖子的图 | 代码只读评论列表、评论数、作者 id、排序策略，没有读任何图片字段。回包里实际有没有：不知道 | 代码；不知道 |
| 详情接口的回包里有没有图 | 供应商的接口说明写着：图文笔记回「图片列表」，视频笔记回「封面图」。linkcheck 的探针工具把 `images_list`、`image_info_list`、`cover` 当成详情里的杂项键剔掉，说明写这段代码的人见过这些键 | 供应商公开文档；代码：`tools/probe_channel.py` |
| 图片列表里每一项长什么样，第一张是不是封面 | 不知道。仓里唯一带 `images_list` 的夹具是测试里手写的一行（`[{"url": …}]`），不是存下来的真实回包 | 夹具（合成的）；不知道 |
| 这些东西现在有没有留下来 | 没有。详情只留四个互动数和审核标记，其余当场丢掉；没有任何地方存原始回包 | 代码：`providers.py` `_tikhub_normalize` |
| 图片链接会不会过期 | 不知道。没有存过一条真实的链接，也没有文档说明 | 不知道 |
| 要拿到 309 篇的封面链接，花多少 | 每篇调一次详情接口：0.010 美元，按 linkcheck 的汇率约 0.072 元，这个接口不打折；309 篇约 22 元。帖子已删的照样计费 | 代码：`providers.py` 的单价表和注释 |
| 拿到链接之后下载图片要不要钱 | 不经过供应商，不收供应商的钱。但它是向小红书的图片服务器发请求，linkcheck 和 TV 现在都没有这样的请求；能不能直接下载、要不要带特定的请求头：不知道 | 代码；不知道 |

结论：**现在付的钱里拿不到**。评论接口那一路不带图；详情接口带，但默认关着，开着的时候图片字段也被丢掉。要拿这 309 篇的封面，得另外花一笔（约 22 元的详情调用），并且先用几篇付费调用量清三件不知道的事：图片列表的形状和顺序、链接多久过期、图片能不能直接下载。这是一个新的小试验，没有做，记在 OPEN-ITEMS I-35，等首图试跑有了结论再问 owner 要不要做。

## 8. 守卫

`scripts/check_first_image.py`（CI 里跑，全是合成数据，不连网）：题库结构、取哪个附件、抽样、答案校验、过线判定、token 硬上限、整个试跑走一遍（假下载、假模型）并查输出里没有任何客户材料、飞书下载、`call_claude` 不带图时请求体不变、workflow 只能手动且默认干跑。

## 9. 试跑之前不知道的

- 飞书应用现在的权限给不给下载素材；开了高级权限的表要不要额外的参数。
- 中转站从 GitHub runner 收不收图片。
- 真实的 token 数、花费、每次调用多久。
- 库里存的图片的像素大小（像素上限暂定 1.2 亿，量过最大的文件再定）。
- 答案有多一边倒。
- 每张表里运营是不是先传封面。
- `c0:raw_extra->内容配图` 这种只取一个键的取数写法对中文键灵不灵。不灵的话脚本自己退回取整个 `raw_extra`，慢一些。
- `scripts/requirements-first-image.txt` 里两个库的版本范围没有在本机装过（开发环境不联网）。
