## 4. 每晚怎么跑，钱怎么封顶

单独的 workflow：`.github/workflows/first-image-sync.yml`（**First image sync**），脚本 `scripts/first_image_pass.py`。

- 定时：每天 15:37 UTC（北京 23:37），排在夜跑同步之后。起跑会漂，漂了不要紧：今晚没赶上的帖明晚做。
- 手动：输入 `mode`（`nightly` / `cards`）、`dry_run`（默认 `true`）、`max_images`（只能调低）。`cards` 是一次性把经验卡背后的帖做完；不点也行，每晚那一趟也会先做经验卡的帖。干跑不下载、不调模型、不写结果，只把题库里的三张名单同步进库、报这一趟有几篇要做。
- 每晚做哪些：有首图、没做过（或者图换了、到了重试时间）的帖里，经验卡背后的帖，加上新帖。经验卡的帖排前面。运营后补图的新帖，补上之后的那一晚做。
- 什么算新帖：2026-11-16 之后第一次入库，并且下面两条占一条。一，有发布时间，而且入库时发布还不到 30 天。二，还没有发布时间（运营刚建的行），而且这个项目在它入库的 7 天之前就已经有帖在库里。第二个条件防的是整张表刚接进来、或者删了重灌：那时候几百篇老帖的入库时刻全是当天，只看入库时刻会把它们全当成新帖，一晚 40 张地补下去，那是 D-157 不许的回头补。这样的表里，发布超过 30 天的不做；没有发布时间的，等填上发布时间再看。
- 一张图的过程：按 `file_token` 从飞书下载到内存 → 缩成长边 1,024 的 JPEG（元数据随之丢掉）→ 问模型 → 校验 → 结果一次写进库。

**钱的上限写死在代码里，每次调用之前查，会越线的那一次不发，之后也都不发：**

| | 图片数 | token（输入当量 = 输入 + 5 × 输出） | 按价格表合多少 |
|---|---|---|---|
| 每晚（`nightly`） | 40 张 | 750,000 | 约 0.97 元 |
| 一次性（`cards`，只能手动） | 60 张 | 1,500,000 | 约 1.94 元 |

- token 上限怎么算的：`min(写死的数, 元数 ÷ 价格表里便宜档每个输入当量 token 的价)`。便宜档输入 0.10 美元 / 百万 token，乘中转站倍数 1.8、汇率 7.2，是 1.296 元 / 百万；1 元合 771,604 个，写死的 750,000 比它小。价格表（`scripts/model_prices.py`）涨价，上限自动跟着降；降价不会把上限抬过写死的数。倍数和汇率是假设值，没对过账单，所以这里的「元」都是按假设价估的；token 数是实数。
- 一张图开始之前，先看它 7 次调用的预留（约 75,000）放不放得进去，放不进就不开始。预留是往多里留的：图片按纸面公式的 2 倍，输出按 `max_tokens` 满打满算。没回报用量的调用、失败的调用按预留记。
- **只调便宜档。** 每次调用之前再核一遍模型名：不是试跑配置里的便宜档，或者它不是价格表里最便宜的模型，就不发。脚本没有换模型的参数，也不从环境变量读模型名。
- **一次预留对一个真发出去的请求。** 每次调用只试一次，SDK 自带的重试关掉，只走主中转站。夜跑用的备用中转站（D-148）这一步不用，workflow 也不传它的钥匙：那条路主站没答成会再打一次备用站，一次调用发两个请求，第二个不在账上。脚本开头自己把 `RELAY_FORCE` 定成 `primary`；配了备用站又没定成 `primary` 的话，一个请求都不发。代价是主站不通的那一晚不做，下一晚再来。
- 预计实际花多少（按试跑每次调用约 0.0025 元估，没量过 fi-v0.2）：一张封面约 0.02 元；每晚新来的带图帖约 13 张（没去掉先不做的三个项目），一晚约 0.25 元以内；经验卡那 32 篇一共约 0.6 元。
- 上限是按「一趟」算的。定时一晚只起一趟（守卫钉着 cron 只能是一天一趟）；有人手动再点一趟真做的（`dry_run=false`），那一趟有它自己的一份上限。手动默认是干跑。
- 另有时间上限 40 分钟（首图那一步 55 分钟、job 75 分钟）。模型调用连着失败 6 次就停；结果写不进库也停。
- 一篇帖卡不住整趟。飞书不给下载、或者模型两次都没答成的那一篇，先记一笔不算数的失败再往下做：它下一晚排到没做过的帖后面，一共试满 6 次不再试。不记的话它每晚都排第一，后面的帖永远轮不到。只有这一趟开头连着两篇不同的帖都这样（还没有一张图下载成，或者还没有一次调用答成），才当成凭证或中转站的问题停下来；这两篇也各记了一笔。凭证真坏了的那几晚，每晚有两篇帖各多记一次不算数的失败。

**不拦任何夜跑。** 它是单独的 workflow，和 `daily-sync`、`features-sync` 不共用 job、锁和行。首图那一步自己也不会让 job 变红：迁移没跑、缺 secret、图片库没装上、飞书或中转站拒绝、到了上限，都只打一行说明，退出码是 0。它做没做成，看那次运行的 Summary。没有新的环境变量和 secret，用的都是夜跑已有的。看门狗名单里加了它，盯的只是「定时有没有触发、job 有没有跑完」；有人在 Actions 里把它停用了，看门狗认得，只说一声，不报红（只对首图这一趟这样，夜跑那几趟被停用照样红）。

**图片是客户的材料**：只在 runner 的内存里，不写盘、不进 artifact（workflow 里没有上传步骤）、不进日志、不进库。日志和 Summary 里只有计数和状态词，没有 note_id、标题、封面上的字、文件名、`file_token`、链接、中转站地址、报错正文。

失败怎么处理：

| 情况 | 记成 | 之后 |
|---|---|---|
| 第一个附件是视频 | `first_is_video` | 定了，不下载、不问 |
| 超过 48 MiB | `too_large` | 定了 |
| 下载到了但解不开 | `decode_failed` | 定了 |
| 模型说不是封面 | `not_a_cover` | 定了，只存「是不是封面」那一个答案 |
| 飞书不给下载（文件没了、这张表没权限） | `download_failed` | 约 20 小时后再试，第二次之后约 44 小时，满 3 次不再试 |
| 飞书说没权限，而这一趟还没有一张图下载成 | `download_failed` | 分不清是这个文件的事还是凭证的事：约 20 小时后再试，不算进那 3 次，一共试满 6 次不再试 |
| 模型问了，但「是不是封面」没答成 | `no_answer` | 约 20 小时后再试，第二次之后约 44 小时，满 3 次不再试。为什么没答成，Summary 里按写死的词分开数（第 10 节） |
| 是封面，七次都问完了，但答案自相矛盾（三条自检规则） | `answered` | 定了。只把有关的那几道题记无效（`inconsistent:<规则名>`），别的题照存，不重试（D-160，第 11 节）。11-16 那一版是整轮作废、记 `no_answer` |
| 说了没有字，抄出来的又是一句「没有」的话（`无`、`没有`、`空` 这类写死的几种） | `no_answer` | 两次调用说的是一回事，不是真的对不上：和 D-160 之前一样整轮作废，约 20 小时后再试，第二次之后约 44 小时，满 3 次不再试（第 11.2 节） |
| 网络断、中转站出错 | `download_failed` / `model_failed` | 约 20 小时后再试，不算进那 3 次；一共试满 6 次也不再试 |

运营换了图，下一晚按新图重做，旧答案先删掉。「定了」的那几种，换了图也会重做。换了图、还没轮到重做的那一会儿，读的那一面不给出旧答案（`image_changed`）。

做完之后运营又往同一列里加了图、第一个附件没变：不重做，也不重新问模型。但它现在是多图的帖了，读的那一面立刻按多图的规矩走（`cover_unconfirmed`），项目没被确认就不给出答案。

## 5. 要 owner 跑的 SQL（一份）

`schemas/notes_v1_28_first_image.sql`。在 Supabase SQL editor 整份跑一次，可以重跑。全是加法：两张新表、三个函数、两张视图，不改任何已有的东西。

**这份 SQL 就是开关。** 没跑之前，每晚的首图步骤打一行「迁移还没跑」就结束，不下载、不调模型、不花钱。跑了之后，下一晚开始做。先合代码还是先跑它都可以。要停：在 Actions 里把 **First image sync** 停用，看门狗不会因此报红。

停用期间改了题库里的名单（比如把一个项目加进「先不做」），名单要进了库，读的那一面才知道：手动点一次 **First image sync**（默认就是干跑，不花钱），它会把名单同步进去。没停用的时候不用管：只要连得上库，每晚都同步，缺钥匙、图片库没装上、便宜档配置被拒的那几晚也同步。

库里多了什么：

- `truth_vault.note_first_image`：每篇做过的帖一行。读的是哪一列、第一个附件的指纹（`file_token` 的 sha256，不是 token 本身）、几个附件、结果、试了几次、下次什么时候再试。
- `truth_vault.first_image_bank_state`：只有一行，题库文件里三张名单的镜像，首图步骤每晚开头写一遍。
- 答案还是存在 `truth_vault.note_feature_answers`，`run_tag = 'img-primary'`。文字题库的视图只读 `run_tag = 'primary'`，碰不到这些行；首图答案不进闸二、不进打分器。
- 封面上抄下来的那句大字（`img_main_text`，最多 40 字）也存在这张表里，和帖子正文一样留在库里（设计 5.6 节），但不往外给。
- `truth_vault.v_note_first_image_source`：哪一列、哪个附件算首图。规则只写在这里：`内容配图`、`笔记配图`、`图片` 里第一个非空的，取第 0 个附件。
- `truth_vault.v_first_image_features`：给下游读的那一面，第 6 节。

两张表开了行级安全、没有策略；表、视图、函数都只给 `service_role`。

查进度（SQL editor）：`select status, count(*) from truth_vault.note_first_image group by 1;`

## 6. 下游怎么读（给写作台那一步的契约）

经验卡的封面那一行、写作台的那一句封面建议，这个 PR **都没做**。它们一部分在写作台仓，是后面单独的一步。TV 这边做到「有一面稳定的东西可读」为止。

读 `truth_vault.v_first_image_features`（只有 `service_role` 能读）。每篇**做过的**帖一行，`note_id` 就是经验卡的 `source_note_id`。

| 列 | 类型 | 会不会是 NULL | 含义 |
|---|---|---|---|
| `note_id` | text | 不会 | `truth_vault.notes.note_id` |
| `project_id` | text | 不会 | TV 的项目名 |
| `status` | text | 不会 | `answered`、`not_a_cover`、`first_is_video`、`too_large`、`decode_failed`、`download_failed`、`no_answer`、`model_failed` 之一（第 4 节的表） |
| `usable` | boolean | 不会 | 这一篇的首图答案能不能用。`true` 的条件：`status = 'answered'`，不是「多图且没人确认」，项目没被列为先不做，题库镜像在而且版本对得上，做完之后首图没换也没被拿掉 |
| `cover_unconfirmed` | boolean | 不会 | 多图的帖（`n_files > 1`），而且它的项目不在 `cover_confirmed_projects` 里。只有一张图的帖永远是 `false` |
| `project_excluded` | boolean | 不会 | 这一篇的项目现在在 `excluded_projects` 里 |
| `n_files` | integer | 不会 | 帖子**现在**图片那一列里有几个附件（读的那一刻数的，不是做的时候记下的数）。图片列整个没了时，给做的时候记下的数 |
| `bank_version` | text | 不会 | 做这一次用的题库版本（`fi-v0.2`） |
| `model` | text | **会** | 答题的模型名；没调过模型（视频、太大、没下载到、解不开）是 NULL |
| `checked_at` | timestamptz | 不会 | 这一行最后一次写的时刻 |
| `answers` | jsonb | **会** | `usable` 为 `true` 时是对象 `{题号: 答案}`；`usable` 为 `false` 时是 NULL |
| `image_changed` | boolean | 不会 | 做完之后第一个附件换了，或者图片列没了：库里的答案是给旧图答的，`usable` 是 `false`。换了图的帖下一晚会重做 |

`answers` 里可能出现的键和取值（都是题库里的原文，闭集）：

| 键 | 取值 |
|---|---|
| `img_layout` | 一张照片 / 拼图 / 前后对比 / 纯文字卡片 / 截图样式 |
| `img_person` | 没有人 / 只有手或身体一部分 / 有人但看不到脸 / 看得到脸 |
| `img_product` | 没有 / 有但在背景里或很小 / 有而且是主体 |
| `img_text_has_number` | 有 / 没有 / 没有字 |
| `img_text_kind` | 提问 / 结果或结论 / 清单或教程标题 / 只是名称 / 没有字 |
| `img_decoration` | 有 / 没有 |
| `img_brand_readable` | 能 / 不能 |

读的时候守这几条：

1. **只用 `usable = true` 的行。** 没有行 = 这篇没做过（没有首图、是老帖、项目先不做、还没轮到）。没有行和 `usable = false` 一样对待：这张卡没有封面信息，卡的其余部分照旧。
2. **`answers` 里没有某个键 = 这道题没答成。** 不要当成「否」，不说这一项就是了。`answers` 可能是空对象。一行 `usable = true` 的帖可能字那几道题一个键都没有（答案自相矛盾，只作废了有关的题，第 11 节）：数的时候按键数，不要按 `usable` 的行数。
3. **不认识的键忽略。** 以后哪道题重测过线，会多出键来（今天可能多出来的是 `img_text_amount`、`img_finish`、`img_scene`、`img_text_matches_title`）。列只加不改。
4. 封面上抄下来的字不在这里，下游永远拿不到。下游也不取图片。
5. 视图不存在（SQL 还没跑）或读失败：按「没有封面信息」走，不拦借卡、不拦出稿，和 `validated_hits` 一样的宽容读法。
6. 一次按 `note_id` 取多行时，`in` 列表走 URL，一批不要超过 200 个（D-080）。
7. 写给写手看的话只说计数，说成「借到的这几篇爆帖里，几篇的封面怎样」，不说成规律、不说成建议照做；借到的卡里 `usable` 的不到三张就不说（设计 5.4 节）；说某一项的时候，分母是 `answers` 里有这个键的卡，不是 `usable` 的卡。答案没有人对着图核过，这句话要留在说明里。
8. `cover_unconfirmed` 和 `project_excluded` 是读的那一刻按题库镜像算的：有人确认了一张表之后，不用等重做，下一晚首图步骤同步完名单就变。`n_files`、`cover_unconfirmed`、`image_changed` 还跟着帖子现在的图片列走：运营加了图、换了图，读的那一面当时就变，不等首图步骤。

## 9. 离线验证不了的

这些都只在假库、一次性的本地 Postgres 和合成数据上跑过，没有碰生产、没有联网、没有调过模型：

- `scripts/requirements-first-image.txt` 里两个图片库在 runner 上装不装得上（开发环境不联网，本机没装 Pillow，缩图那几条守卫在本机是跳过的）。
- 经 PostgREST 调那三个函数（参数和返回的形状）：本机是用 psql 调的同三个函数。SQL 刚跑完的头几分钟 PostgREST 可能还不认识新函数，那一晚会当成「迁移还没跑」跳过，下一晚正常。
- fi-v0.2 的真实花费和每次调用多久；七次调用的问法下模型答得稳不稳；常规图可用的占比会不会还是 0.83 上下。
- 每晚实际有几篇新帖带图；40 分钟够不够做完 40 张。
- 生产库里经验卡背后带图的帖现在是不是还是 45 篇（设计时量的）。
- GitHub 的定时什么时候真的起跑。
- 看门狗问 GitHub「这个 workflow 是不是停用了」的那一次请求，返回的状态词是不是以 `disabled` 开头（按 GitHub 的接口文档写的，本机用假响应测的）。问不到时照旧按「没跑」报红。
- CI 的 sql job 用的是 runner 自带的 `python3`。它没有 PyYAML 的话，`check_first_image_pg.py` 的 B 段（在真库上跑一趟首图步骤）会跳过，只打一条 warning；A 段只用标准库，照常跑。本机两段都跑了。
- 生产库里 `publish_time` 填得全不全。新帖的规则靠它分清「刚发布的」和「老帖」；没填的帖按「项目是不是早就在库里」走。
- 主中转站一个请求超时之后，它那一头有没有照样生成、照样收钱。账上按预留记了这一次。

## 10. 第一次真跑（11-16）：32 张里 11 张没答成；只加了原因计数，回包的读法没有放宽（D-159）

> 这一节是 11-16 当时的样子。之后第二趟真跑有了原因的数，改了两处（整行一字不差的认、自相矛盾只作废有关的题），见第 11 节（D-160）。下面「不认」「整轮作废」「没动的」几句说的是 D-160 之前。

**跑出来的数**（手动，`mode=cards`，题库 fi-v0.2，便宜档）：32 张图，158 次调用，237,558 输入当量 token，约 0.308 元。`answered` 18、`not_a_cover` 3、`no_answer` 11（34%）。试跑（fi-v0.1，同一档，同样长边 1,024）48 张常规图里没答成的只有 4 张。

**原因还不知道，下面的拆法是推出来的。** 18 × 7 + 3 × 1 = 129 次，剩下 29 次是那 11 篇用的；最顺的解是 8 篇在第一次调用（「是不是封面」）就没读出来、3 篇问完 7 次之后因为自相矛盾整轮作废。但失败重试的调用也算在次数里，这一趟又没有记原因，所以 8 和 3 只是推断。11 篇散在 4 个项目里，jpeg、png 都有，文件的样子上和答成的分不开。另外，答成的 18 篇里存下来的行有不少闭集外的答案：`img_scene` 6/18、`img_person` 4/18、`img_layout` 3/18、`img_finish` 3/18。

离线查到的（没有调模型）：

- 提示词里选项的字和代码认的闭集是一样的，没有对不上的地方。
- 代码读回包只认一种样子：JSON 是模板那个样子、题号一字不差、答案和选项一字不差。而提示词说「答案照抄选项的原文」，选项又是带着解释一起打出来的（`- 封面: 给读者看的图…`）；模板里题号那一格写的是「题号」，题目却标着「第 1 题」。照着这些字面去答的回包会被记成没答成。**模型是不是真的那样回，没有证据。**
- fi-v0.2 把「图上有多少字」（第 1 次调用）和「把大字抄下来」（第 4 次调用，单独问）拆开了，三条自检规则原样留着。fi-v0.1 里这两道在同一次调用里，自检是拿一次回包和它自己比；现在是拿两次独立的调用互相比，对不上就整轮作废，七次调用和别的答案都白花。

**这次改的（不改题库文件，题库版本还是 fi-v0.2，已经做完的帖不重问）：**

1. **认什么一个字没变，没有放宽。** `scripts/first_image.py` 的 `parse_answers` 就是首跑时的那个函数，每晚的步骤和试跑都只用它的结果：从第一个 `{` 到最后一个 `}` 是一个 JSON 对象、里面有 `answers` 列表、题号一字不差、选择题的答案去掉两头空格之后和选项一字不差。`封面。`、`「封面」`、抄了选项的整行、`{题号: 答案}` 这种样子都**不认**，和以前一样。存进库的无效原因还是 `parse_failed` / `missing` / `out_of_vocab` / `text_too_long`。同一道题给了两遍的取第一遍，回包撞没撞输出上限不影响读法，也都和以前一样。
2. **原因看得见。** Summary 多四行，只有计数和写死的词：
   - 「没答成（no_answer）的原因」：每一篇一个词，写进库了才数，所以这一行加起来等于 `no_answer` 的篇数。`first_call:` 开头的是第一次调用没读出来，后面的词见下面那张单子。`round:` 开头的是整轮作废：后面是自检规则的名字（题库文件里的），再加一个细项（说了没有字又抄出了字：抄出来的是一句「没有」的话 `said_none_in_words`，还是真的字 `transcribed_text`；说了有字却没抄出来：`empty_text` / `symbols_only`）。
   - 「逐题无效」：`题号:词=调用次数`，答成了的帖里无效的题也数在内。
   - 「回包」：`stop:max_tokens`（撞了输出上限的调用数）、`stop:other`（中转站回的结束原因既不是正常结束也不是撞上限的调用数，原样的字不带出来）。
   - 「假如放宽读法会多读出」（`would_read`）：见第 3 条。
   - 原因只在 Summary 里，不进库：往状态表加一列要迁移，这次不做。
3. **`would_read`：只数，不认。** 对每一个无效的答案，代码另外按格式再看一遍回包，数一数**假如**放宽某一条读法它会不会被读出来。没有放宽：这些答案照旧无效，照旧不进库。
   - `answers:option_with_punctuation`：选项两头多了句读、引号、括号、列表记号、空格（`封面。`、`「封面」`、`- 封面`），去掉之后和恰好一个选项一字不差。
   - `answers:option_line_copied`：抄的是选项在提示词里的整行（`封面: 给读者看的图…`）。
   - `answers:loose_json`：JSON 不是模板那个样子，但题号还是那个题号、答案一字不差（一道题一个对象、最外层是列表、`{题号: 答案}`、JSON 后面的说明里带花括号）。`answers:loose_json_option_with_punctuation`、`answers:loose_json_option_line_copied` 是两条都放宽才读得出的。
   - `replies:loose_json`：上面三个 `loose_json*` 涉及的回包数。一个回包里至少有一个答案真的读得出才数；换了样子但一个答案都读不出的（答案不是字符串、闭集外、撞了上限）不数。
   - 不数成「读得出」的：带问号、叉、删除线、省略号的，话没说完的（`封面。。。`、`封面——`），没勾的框（`[ ] 封面`），打头带感叹号的，同一道题两个不一样的答案，同一个键写了两遍的，结束原因不是正常结束、JSON 又不是一整个模板的。
   - **这个分类器自己会看走眼。** 对抗评审在它身上核实过二十来种认错的样子，这里只补了其中最明显的几种。所以这一行的数只用来决定下一步值不值得放宽哪一条，不能当成「放宽了就能救回这么多」，更不能拿来认答案。它出了岔子只会把词换成 `unclassified`，不会让夜跑停；长过 20,000 字的回包不细看：中转站说撞了输出上限的记 `truncated`，别的记 `reply_too_long`。
4. **细一层的词（每道无效的题一个）**：`empty_reply`（回包没有字，也没撞输出上限）、`truncated`（没读出来，而且中转站说撞了输出上限；思考把上限用完、一个字都没回的也记这个）、`stop_other`（没读出来，结束原因是别的）、`no_json`、`json_duplicate_key`（一个对象里同一个键写了两遍）、`no_answers_in_json`、`json_not_template`（题号和答案都在，JSON 不是模板的样子）、`id_numbered`（题号写成了 1、2）、`id_absent`、`answer_not_text`、`conflicting_answers`（同一道题两个不一样的答案，而取到的那一个无效）、`oov_option_wrapped`（选项两头多了标点）、`oov_option_line`（抄了整行）、`oov_option_with_mark`（字就是某个选项，但带着问号、叉、删除线、没勾的框这类记号，或话没说完、字中间断开了）、`oov_option_plus_more`（选项后面多了字）、`oov_contains_option`、`oov_part_of_option`（只答了选项的一截）、`oov_other`、`text_too_long`、`reply_too_long`、`unclassified`。
5. **没动的**：`answered` 还是要「是不是封面」读出来等于「封面」；读法、提示词、题目、选项、调用分组、每次调用的输出上限、自相矛盾整轮作废的规矩、重试的规矩、钱的上限都没动。

**为什么没有放宽**：这个 PR 起先在格式上放宽了三处（就是第 3 条数的那三样）。对抗评审在放宽的读法里核实了 21 处问题：话没说完的、没勾的框、两个不一样的答案只读到一个、断掉的回包、带否定的话，会被认成答案；两处比原来严；一处在很长的怪回包上是平方级的慢。把不是封面的认成封面比少认一篇贵，而放宽能救回几篇当时一个数都没有。所以撤了，先数。

**钱**：题库版本没升，做完的 21 篇（18 + 3）不会重问。没答成的 11 篇各用掉了 3 次里的 1 次，下一趟自己会排上：全都答成是 77 次调用、约 0.15 元；和上次一样是 29 次、约 0.06 元。读法没变，它们多半还是答不成；这一趟花的钱买的是原因的数。

**下一趟真跑才知道的**：

- 那 11 篇到底是哪几种原因、8 和 3 的拆法对不对（看「没答成的原因」那一行）。
- 哪一条放宽值得加，或者都不值得（看 `would_read` 那一行；数是 0 就说明模型不是那样回的）。

### 11.1 整行照抄：只认和提示词里那一行一字不差的

`parse_answers` 一个字没动（源码的 sha256 还钉着）。在它判了 `out_of_vocab` 的选择题上，代码再看一眼（`first_image.accept_option_lines`），下面五条**全中**才认成那个选项：

1. `parse_answers` 给这道题的是「闭集外」。
2. 它取的那个答案，去掉两头的空白、再去掉至多一个打头的 `- `（提示词自己印的那个列表记号）之后，和**恰好一个**有解释的选项在提示词里的那一行用 `==` 比一字不差。那一行就是 `选项: 解释`，和 `build_prompt` 印的是同一个函数拼出来的。不折全半角、不去标点、不认全角冒号、不认冒号后面少了空格的，多一个字、少一个字、换一个字都不认。
3. 中转站给的结束原因没给，或者是正常结束。
4. 整个回包除了那一段 JSON 之外没有别的字。只许整段包在一个 ``` 或 ```json 围栏里。
5. 那一段 JSON 就是模板：只有 `answers` 一个键、是列表、每一项只有 `id` 和 `answer` 两个键、`id` 是这次问的题而且不重复、`answer` 是字符串、整段没有写了两遍的键。少答一道题可以（那道题照旧记缺）。

3 到 5 看的是整个回包：有一条不中，这个回包里一个整行都不认，照旧是闭集外。它们只管新认的这一种；答案就是选项名字的回包，读法和以前一模一样。

认的范围是数得出来的：fi-v0.2 里有解释的选项 26 个（`img_kind` 3、`img_text_amount` 4、`img_text_kind` 5、`img_layout` 5、`img_finish` 3、`img_person` 3、`img_scene` 3），每个两种写法（带不带 `- `），一共 52 个写死的字符串。没有解释的选项（`有`、`能` 这种）没有「整行」可抄，什么都没多认：`- 有` 照旧无效。

存进库的是选项本身，不是那一行。所以「答成了」还是要 `img_kind` 等于 `封面`；抄的是「后台或数据截图」那一行的帖记成 `not_a_cover`，1 次调用、只存一行。**认整行不会让模型说不是封面的帖变成能用。**

这和 D-159 撤掉的放宽不是一回事：那次是去标点、认换了样子的 JSON，认的范围是一类字符；这次认的是提示词自己印出来的 52 个字符串，没有字符类。评审核实过的 21 种（第 10 节）现在认下来的和老读法逐字相同，守卫逐条钉着。

Summary 多两行，只有计数和写死的词：

- 「整行照抄、和提示词里那一行一字不差，认成选项（题号=答案数）」（`line_accepted`）。
- 「整行一字不差但没认（原因=答案数）」（`line_refused`）：`stop`（结束原因不是正常结束）、`text_around_json`（JSON 前后有别的字）、`not_template`（JSON 不是严格的模板）。

认下来的答案不再数进「逐题无效」和 `would_read`。`would_read` 里剩下的 `option_line_copied` 就是「像整行、但不是一字不差」的。

**没走改提示词那条路。** 把选项的打法或那句「答案照抄选项的原文」改掉，模型也许就只答选项名字了。但那是换了模型看到的字，按这个仓的规矩要升题库版本：升了之后做完的帖在读的那一面全部不能用，直到重问完。做完的帖两趟加起来 32 篇：`answered` 18 + 10 = 28 篇，`not_a_cover` 3 + 1 = 4 篇。照上次的结果重问一遍是 28 × 7 + 4 × 1 = 200 次、约 0.48 元（按第二趟每次约 0.0024 元算）。另外没答成的帖重新算机会（最多约 140 次、0.34 元），改之前最好先小样试一遍新问法（约 280 次、0.67 元，要 owner 点头），三样一共约 1.5 元。试跑的每一条结论都是在老的打法上量的，改了就都不作数；「是不是封面」这道筛子往哪边偏也不知道。这些离线都证明不了。认整行这条路是 0 次调用。下一趟跑完，如果剩下的 `oov_option_line` 加 `line_refused` 还占选择题答案的一成以上，或者 `partial_void` 占封面的两成以上，工程再把改提示词提给 owner。

### 11.2 自相矛盾：只作废有关的那几道题

这一条 D-159 留给 owner 定；这次是 Claude 按 owner 10-16 的长期授权定的（D-119：「所有决定你帮我判断」，只有不可逆、对外、花钱、改写手用的模型这四类要等 owner 一句话）。它不在这四类里：钱的上限没动，重试只会更少；撤回要改两处：把三条规则的 `void` 拿掉，同时去掉 `validate_bank` 里「每条规则必须写 `void`」那一段（只拿掉 `void` 的话，题库检查不过，首图步骤打一行「题库不合法」就什么都不做、不花钱）；已经按这一条定下来的帖不会自己重问，字那几道题要补的话每篇 7 次调用。owner 可以否决（D-160）。

fi-v0.2 的三条自检规则各加了一张单子 `void`：这条规则中了，作废哪几道题。

| 规则 | 什么时候中 | 作废的题 |
|---|---|---|
| `no_text_but_transcribed` | 说了没有字，又抄出了字 | `img_text_amount`、`img_main_text`、`img_text_kind` |
| `text_but_not_transcribed` | 说了有字，抄出来是空的 | `img_layout`、`img_text_amount`、`img_main_text`、`img_text_kind` |
| `text_card_without_text` | 说是纯文字卡片，又说没有字 | `img_layout`、`img_text_amount`、`img_main_text`、`img_text_kind` |

- **两头都作废，不信哪一边。** 没有「以抄下来的字为准」这种规矩。
- `img_text_kind` 没有被哪条规则点名，也作废：它往外给，而它的前提（图上有没有后期加的字）正是对不上的那件事。
- 靠 `img_main_text` 算的两道代码题（`img_text_matches_title`、`img_text_has_number`）不算了，存 `source_invalid`。第三条规则连大字也作废，就是为了这个：只作废版式和字数的话，空的大字会算出 `img_text_has_number = 没有字`，等于悄悄信了一边。
- 第二条规则连 `img_layout` 也作废，理由一样：「纯文字卡片」（没有照片，只有底色和字）说的就是图上有字，留着它等于信了「有字」那一边（评审找出来的：第一版只作废了三道字的题，这种帖会把「纯文字卡片」往外给）。第一条不用作废版式：那时候版式要是纯文字卡片，第三条也中，版式已经作废；别的版式不说有没有字。第二条里版式是什么都作废（只在纯文字卡片时作废要多写一种「有条件的作废」，没这么做），代价是这种帖连「一张照片」这样的版式也丢了。
- **说了没有字、抄出来的又是一句「没有」的话**（`无`、`没有`、`空`、`none` 这类写死的几种，就是第 10 节的细项 `said_none_in_words`）：两次调用说的是一回事，只是没给空字符串，不是真的对不上。这一种不走「只作废有关的题」，和 D-160 之前一样整轮作废、记 `no_answer`、按日程重问：下一次给了空字符串，就是一整套对得上的答案。只作废的话这一篇就定了，字那几道题再也不问（评审找出来的）。第二趟这样的 0 篇。
- 作废的题存空答案，无效原因是 `inconsistent:<规则名>`；本来就无效的题留着本来的原因。几条规则都中，作废的题取并集。规则都对着同一份答案看，前一条作废的题不影响后一条怎么判。规则中了的帖，留下来的答案里没有一个在说图上有没有字（字数、大字、字的种类、两道代码题、纯文字卡片）。
- **别的题照存，这一篇记 `answered`，定了，不重试。** 还是 13 行。`img_kind` 不进任何规则（题库检查钉着）：是不是封面只看它自己的答案。
- 没写 `void` 的规则还是整轮作废。fi-v0.1（试跑的那份，文件钉着没动）就是这样，试跑的结果不受影响。
- 每晚的步骤不收没写 `void` 的题库（题库检查）。

Summary 多一行：「自相矛盾只作废有关的题（规则:细项=帖数）」（`partial_void`），细项还是第 10 节那几个词。「没答成的原因」里 `round:` 开头的只剩 `round:no_text_but_transcribed:said_none_in_words` 一种。

**下游看到什么**（第 6 节的契约没变）。只有一张图的帖，说了没有字、又抄出了字：以前是 `no_answer`、`usable = false`、`answers` 是 NULL、过一天重试；现在是 `answered`，`usable` 的条件和以前一样，`answers` 比如是 `{"img_layout":"一张照片","img_person":"没有人","img_product":"有而且是主体","img_decoration":"没有","img_brand_readable":"能"}`，里面没有 `img_text_kind` 和 `img_text_has_number`。说了有字、抄出来是空的：`answers` 里连 `img_layout` 也没有。没有这个键就是这道题没答成（第 6 节第 2 条），不是「否」。说了没有字、抄出来的是「没有」：和以前一样，`no_answer`、`answers` 是 NULL、过一天重试。

### 11.3 版本、重问和钱

- **不升题库版本。** 题、选项、分组、提示词一个字节没变。新代码不会把一道题的有效答案换成另一个值：要么在老代码给不出答案的地方多给一个（11.1），要么在一轮里留下本来会整轮作废的答案（11.2）。反过来也可能少：整行认出了字数「没有字」、大字又抄出了字，第一条规则这时作废字那几道题，老代码会把它们存下；大字写「无」的那种整轮作废、`no_answer`。只会更少或更多，不会变成别的值，所以不升版。题库文件加了 `void`，所以 `bank_sha256` 变了（和改名单一样，下一晚同步进库）；改动之后写的行可以凭它和之前的分开。
