## 3. 第二批

原则：**能用代码做的不交给模型，能用代码查的不交给 Jev；全部只提示，不挡存档。**

### A · 版式由代码拼

- 每个项目一份交付模板，存在 `projects.default_params` 的 `delivery` 键里（不加列、不加迁移；运维用 aw `deskcore.cli delivery-format` 设，写回时合并，不能把已有的隔离词冲掉）。**没配模板的项目回包里没有 `delivery`**，写手照旧按规则自己排——不存在「默认版式」。
- 模板能配的（aw `deskcore/delivery.py`，`docs/deskcore.md` §3.9）：表格（`table`，列只认 `direction` / `post` / `comments`）或一篇一段（`blocks`）；标记钉死【标题】/【正文】（tv-sync 只认这两个，运营贴的也一直是这个）；`post` 一格里是 【标题】标题 + 【正文】正文 + 话题行。**标题单独一列（TGV 那种）配不出来**，要接这种项目得先改 aw 的 `delivery.py`。话题是写手给的几个 + 固定的 + 按词触发的，顺序由模板定（话题顺序归这里，不归 B）。
- 写手把标题、正文、话题、评论、方向作为单独的字段交，`score_drafts` 存档后按模板拼好整段交付文本（`delivery.text`）返回，写手原样贴给用户，不再自己排版。
- 方括号标记是机器字段，不受 human-writing 的标点禁令管；标题、正文的内容照旧受管。
- **回包里没有 `delivery` 时没有退路**：`score_drafts` 出错（409 锁等超时、库错）、一篇都没存进去、模板写坏了（只记日志、这次不拼），都没有 `delivery`；协议让写手「照项目规则自己排」，`open_project` 的简报里不带模板。
- 所以模板接管之后撤规则表里的交付格式规则（先备份）要分两半：互相打架的那几条撤掉；留一条和模板一致的短规则（只写【标题】/【正文】标记和话题行放哪）当上面那种情况的退路，直到 aw 让简报带上模板（或它的一句话版式）为止。在那之前全撤，`score_drafts` 一失败版式就又回到模型即兴排——正是 A 要去掉的（OPEN-ITEMS W-28）。

### B · 能数能比的规则由代码查

- 规则表早就有结构化的列（`rule_kind` / `rule_payload`：禁用词、必含词、字数上下限、禁用正则），292 行里一行都没用。Jev 不会数数、比大小、算日期（jev:docs/31），这类规则只能代码查。
- 把能结构化的规则（字数、禁用词、必含词、禁用正则）补上结构；交稿时代码逐条核，回包里点名哪条没过、哪一处。毫秒级，不调模型。
- 代码查只认这四种（aw `rulecheck.CHECK_KINDS`：forbidden_word / forbidden_regex / required_phrase / max_len；max_len 管字数上下限，`min` / `max` 至少给一个，同 D-121），别的 `record_rule` 直接回 400。**话题顺序不归这里**：它由 A 的模板定（`tags.fixed` / `conditional`），WTG 那条话题顺序规则在模板接管后跟着交付格式规则一起撤。
- 规则原文照旧在简报里（写手得知道）；代码核对是多一道提示，不改参考分、不拦存档。

### C · 简报带最近稿子的结构分布（`recent_structure`）

- 写作台存的稿，Jev 打参考分时已经把 20 道特征题的答案写进了 TV 账本（`note_feature_answers`，`subject_type = aw_version`），写作台自己把它们丢了。直接从账本读，不多调一次模型。
- `open_project` 的简报里给本项目最近一段稿子在几道结构题上的分布，某个取值占了一大半时说一句「这批换一种」。题目、窗口、阈值以 aw 的 `deskcore/structure.py`（`docs/deskcore.md` §3.1）为准，现在问的是：正文第一句是哪一种、标题是不是问句、有没有前后转折、有没有写到已经发生的坏结果、有没有拿别人和自己对照、有没有点名某一类读者。
- **故意不问的**：叙述人身份、亲身经历（已发笔记 81% / 86% 都是「是」，题库的 aw_instruction 还要求交代一个身份——稿子扎在这边是常态，叫一半稿子换掉是把它们往偏离已发笔记的方向推）；具体时间 / 地点 / 引语 / 身体感受这类具体性题（扎堆在「有」是好事）；产品在文中的角色（怎么扎堆都是项目露出要求定的，不是写法习惯，产品向项目里产品就该是主角，D-121）。
- **已验证规律用到的题一律不报**：求助、结尾问读者是下发的规律，第一批让模型按篇轮换着用（`validated_patterns_usage`），扎不扎堆归那条轮换管；这里再报就是两条指令在同一份简报里打架。
- 只是提示，不强制每批换、不拦存档。

### D · 写作台用上率灯（TV 仓，本次实现）

脚本 `scripts/check_desk_use_rate.py`，哨兵 `DESK_USE_RATE_CHECK_DONE`，daily-sync 每周一（北京）跑，手动触发照跑。只读。

| 口径 | 怎么算 |
|---|---|
| 窗口 | 发布于 21 天前 ～ 7 天前。晚 7 天：稿子发出去要等 tv-sync 夜里对上，看太近会把「还没对上」读成「没接住」。两个数都能调 |
| 发布 / 对过账 | TV 项目窗口内发布的笔记（飞书里已删的不算，`v_notes_vanished`，同闸二 / 策展 / 通道 1）/ 其中 `tv_note_links` 有一行的（正常两者相等） |
| 发牌 / 在用期 | 发牌看窗口起点前 7 天到窗口终点：牌先发、稿后存、帖再发（10-20 生产上接住的帖，存稿到发布 p50 1 天、p90 4 天、最长 38 天），只看窗口内会把起点前几天发的那批读成零动静。在用期 = 这个项目每张牌那天起 7 天，加上每篇接住的帖存稿那天（发布日 − `lag_days`）起 7 天，按日算、可以断成几段；判据只数在用期里发布的帖。首牌之前、末牌 7 天之后、中间停了一阵的那几天发的帖基本不可能是写作台的稿：只在回看里发过一张牌、之后再没动的项目，不拿整窗手写的帖判它。接住的帖本身证明那几天写作台在出稿（翻旧牌写、没抽新牌，或那批牌在回看之外），那几天照判。7 天和回看同一个理由：p90 4 天，盖住九成还有余量；不为 38 天的尾巴放长，放长了停用的项目会被当成在用。表里的发布、对过账两列照旧数整个窗口 |
| 接住 | 对上写作台存档（body_exact / title_exact / fuzzy / edited / tv_lineage），且写作台那版不晚于发布 |
| 未改动 | 接住且算过当前口径差异（`diff_rev ≥ 2`）的里面，`changed = false` 的。全库还没有这个口径的行时打「未改动率: 待重算」 |
| 亮黄（rc=1） | 写作台在用（回看期内发过牌，或窗口里有接住的帖）、在用期里发布的帖对过账 ≥15 篇且占在用期里发布八成以上、其中接住率 <20%。够不够格判只有一条规则，亮黄、「没有项目够格判」和 ✓ 那句用同一条：唯一在用的项目对过账不到八成时，报「没有项目够格判」加判不了，不打 ✓ |
| 判不了（rc=2） | 映射的 TV 项目一篇没发，或发了一条链接都没有（tv-sync 没跑）；或者某一个项目整窗发布 ≥15 篇、对过账不到八成（tv-sync 漏了这个项目——aw 的 tv-sync 一个项目出错只记一行、接着跑别的，合计看不出来），点名报；发过牌的项目在用期里发布 ≥15 篇、对过账不到八成的也点名（tv-sync 从某天起坏、这个项目又正好从某天起才用写作台，整窗合计还过八成）。对过账够 15 篇、却因为对账不全不够格判的项目一定被点名，不会安静跳过。别的项目照常判，有项目亮黄时 rc 仍是 1 |

- 回看期内一张牌都没发、窗口里也没有一篇接住的项目不归这盏灯，归角度台账灯判据 C，不重复喊。没抽新牌、翻更早的牌写出接住的帖的算在用：接住本身就是证据。
- 在用的项目两盏灯可能同一个周一一起亮：判据 C 的「连上了、写完没存档」也报在用的项目，两边读的是同一批 `tv_note_links`，光凭链接分不清「没存档」和「被重写」（两种发出去的都是补录副本）。分开它们看写作台这段时间存没存这个项目的稿（判据 C 那张表的「真稿」列）：真稿接近 0 是没存档，按判据 C 那边查；存了不少稿、发出去的仍对不上才是被重写，修在本文第一批 / 第二批。D 亮黄的报文里写着这一句。
- 「未改动」很严：标题改了、正文差一个字都算改过，所以另报改了标题的篇数。
- 谁看：owner 每周一随 OPEN-ITEMS 例行检查看一次；红了修在 autowriter 仓（本文第一批 / 第二批），TV 这边改不好。

### E · 自由文本规则编成 Jev 是非题 —— owner 10-20 全部放行（D-121）

**原来卡在哪**：Jev 的数据政策（jev:docs/00 #7）不许未发布的客户内容出境，`project_layer_cleared` 是空的，草稿上的项目层题对所有项目都被丢掉。

**owner 10-20 定了（「全部放行，一次到位」，D-121）**：

- `project_layer_cleared` 改成 `["*"]`，所有项目放行；Rx 闸不变（`rx_cleared` 不认 `*`），jev:docs/00 #7 记了勘误。
- 规则原文可以发给 Jev 编题（新接口 `POST /compile_rules`，只认管理 key）。
- 规则题的结果**从第一天起就给写手看**，硬规则记「必须改」、软规则记「建议改」，都只提示、不拦存档。
- 软规则从简报开头挪走，仍要等下面第 5 步标定过线才做。

做法：

1. **编题**：每条自由文本规则编成 1～3 道是非题，题号里带规则 id 和内容哈希（规则一改就是新题号，旧答案留着；Jev 格式的题版本号恒为 1，不能靠它区分）。能数能比的规则不编，走 B。
2. **怎么发**：作为内联 `project_bank` 发，**不放进 `brief.hard_rules`**（那条路会给每题默认一个「要否」，变成硬规则，算进是否通过和参考分）。
3. **单独 run_tag**：一次 `/judge_draft` 的所有行共用一个 run_tag，影子题要单独发一次请求、用自己的 run_tag，不和 `primary` 混。
4. **不进存档那条路**：存档的判定预算 10-20 只剩约 1.8 秒（一批 20 篇有 6 篇超时）。影子题在存档返回之后异步跑。
5. **标定**：拿 `tv_edit_diffs` 里发布前的人改（`lag_days ≥ 0`、`diff_rev ≥ 2`）对：Jev 说违规的那句，人改了没有。能用的改稿对只有约 100 对，按规则类型合在一起算，不按单条。
6. **之后才动简报**：标定过线的那类软规则，才从简报开头挪出去，改成交稿后 Jev 查。

原来没定的两件，10-20 定了：**Jev 的生成器编题**（`/compile_rules`，一批 10 条、6 批并行）；**编好的题存在规则行的 `rule_payload` 里**，按规则内容哈希认，规则一改就重编。写作台侧给写手一个查规则的工具，打分之后调、按结果改、再打分（autowriter 仓，D-121）。

### F · 分段判 —— 不做

稿子太短：近 14 天中位 163 字，中位段数 1；SPX 中位 95 字，98 篇里只有 10 篇有换行。Jev 按换行切段、逐段串行判，项目层题的证据只从正文挑。等多数项目的稿子变长、变成多段再议。

## 5. 风险

1. **灯的数小、噪声大。** 一个项目两周常常只有二三十篇。所以有 15 篇下限、14 天窗口，单周的起落不下结论，看三四周的走向。
2. **「接住」靠 tv-sync 的匹配。** 被整篇重写的稿对不上，算没接住——这正是要量的。fuzzy / edited 错配会让接住率偏高；ambiguous 不算接住。
3. **「未改动」可能长期很低。** 运营改几个字是正常的，它不该是唯一的目标；看它往哪走，比看绝对值有用。
4. **别让数变成目标。** 这盏灯只给 owner 看，不给写手看，不进写作台的分数。原样发多了不等于稿子好了。
5. **A 的代价**：回包变长（大回包曾把协议挤出模型的注意力）；改协议要写手重导 skill；旧的交付格式规则不撤会和模板打架，全撤了又没有退路——`score_drafts` 一失败、回包没有 `delivery`，版式就回到模型手里（§3 A，W-28）。
6. **B 的代价**：规则补结构时抄错会误报；所以只提示，补结构前备份。
7. **C 量到的可能是第一批自己。** 所以已验证规律用到的题 C 一律不报（第一批的轮换管它们）。Jev 对草稿的答案和 TV 的 Sonnet 口径不完全一样（D-105 的一致率表），超时的稿也有答案行。
8. **E 的风险**：数据政策；存档预算已经很紧；标定样本只有约 100 对；Jev 的题版本号问题。
9. **212 条「发布后才存进写作台」的版本，为什么会存进去还没查。** 灯和改稿差异都已排除它们，但根因不在第二批里。
