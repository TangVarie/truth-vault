### 0.1 曝光 / 阅读 / 互动：表里有，但是**事后加**

> owner 原话：「带曝光/阅读/互动，只不过是事后加，不是每次一开始就有，现在应该是能在表里读到的」

**这让风险 #3 变难了，不是取消。**

原判：这三列不在文档 36 列里 → 要给 17 个项目各写一份 `capabilities_absent`。
更正后：列在，但**新表首轮同步时这三列会整列为空**（帖子刚发，数据还没回填）。

而要害字段的判据是「**整轮 notes 里一条都没值**」，不是「列不存在」：

```python
# scripts/sync_feishu_notes_to_truth_vault.py:500-519
def _detect_missing_capabilities(notes, platform=None):
    """整轮 notes 里**一条都没值**的要害字段 → [(列名, 中文名), ...]"""
    ...
    if not any(n.get(col) not in empty for n in notes):
        missing.append((col, label))
```

→ **新表第一晚照样红**，只是走的是另一条路。

而 `capabilities_absent` **救不了**它。第三条硬规矩（`:546-548`）：

```python
if col in mapped:
    raise ValueError(f"{pid}: capabilities_absent 声明 {col} 产不出, "
                     f"field_mapping 却映了一列到它 —— 二选一")
```

新表**有**这三列，只是暂时空。映了列就不能声明豁免；声明豁免就不能映列 —— 而不映列的话，
数据回填之后也读不到。**两难。**

**根因：现有机制只有两档，缺第三档。**

| 状态 | 现有表达 |
|---|---|
| 有列、有数据 | 正常 |
| 结构上永远没有这列 | `capabilities_absent`（D-056） |
| **有列，这轮还没数据，但会有** | **表达不了 → 被当成第二档判红** |

D-056 定的是「要害字段整列产不出来 → 直接红，不给认领」，针对的是"这张表永远不会有"。
新表是"暂时没有"。

**两个候选解法**（要 owner 定）：

- **A. 按行龄判。** 发布不满 N 天的行不计入 capability 判定。
  自愈、不依赖人记得撤销豁免，贴合"数据事后加"的现实。
- **B. 加 `capabilities_pending`。** 声明"这轮空是预期的"，但计数，M 轮后仍空则红。
  更显式，但依赖人记得撤 —— 而 D-053 的教训是**会被忘掉的闸等于没有闸**。

倾向 A。但 N 取多少要看真实回填节奏，**本会话没有数据**。

# 统一飞书表接入评估 · 给 owner 的结论

数据基准：2026-09-22 实查生产库 `truth_vault`（notes 6197 行、爆+大爆 397 行、audit_log 152 MB），代码基准 `/home/user/truth-vault` 当前 HEAD。

## 1. 一句话

**接，是净赚，但要先修两个函数——否则赚的是新维度，亏的是飞轮燃料的可信度。**

躲不开 ≠ 会断：25 个监控列一列不声明也只是"绿 + 一条黄注解"（D-055 后 `undeclared_fields` 隔离实测 **0 行**，BJS 182 行已把整套 22 个监控列吞进 `_undeclared` 预演了三个月）。真正的账在两头——**亏的一头**是这张表把 `流量状态` 从"运营手写、基本不动"变成"机器每轮重算的六档"，而 TV 的 tier 引擎是**单调不降**的、ssll 通道是**单向不回收**的，今天已经有 **285 行**降档残留躺在对面库里、占 TV 注入样本的 48%；**赚的一头**是它白送了 TV 现在**完全没有**的四个维度（观众真实评论、事件时刻、速度、蓝词闭环），而且其中三个的容器已经在库里躺着了。

## 2. 最大的那颗雷：tier 只升不降 + ssll 只推不撤

### 是什么

两段机制咬在一起，任何一段单独看都不致命：

**第一段 · tier 单调不降。** `流量状态` 是多选且**追加式**（`scripts/_common.py:392-394` 本仓自述："运营的多选状态是追加式的（`['评估中','无水花']` = 先评估、后判死）"），生产实证一个格里堆着这帖走过的全部历史档位（OKMAN 2 行 `['无水花','评估中','爆帖预备','爆贴']`、16 行 `['评估中','爆贴']`）。而 `extract_tier`（`_common.py:436-453`）逐 token 判档后 `max(hits, key=_TIER_RANK)`，`_TIER_RANK`（`:395`）是 `大爆8 > 爆7 > 预备6 > 参考5 > 风控4 > 趴3 > 评估中2 > 未知1`。

→ 一条到过"爆贴"的帖后来被限流，格子变成 `['爆贴','风控中']`，TV 判 **爆**。生产已有 **4 行**这个形状（今日实查），其中 3 行 `tier=爆`（OKMAN×2、SPX×1）且 **3 行全部 `on_shelf=true` / `is_curated=true` / 已推 ssll**。而文档明写"刷新时已有『风控中』标签不可覆盖"——这是永久 latch，上线后这个形状只会单调增长。

**第二段 · ssll 只推不撤。** 推送闸 `scripts/sync_truth_vault_baokuan_to_sanshengliubu.py:145-148` 是一次性的（靠 `synced_to_ssll_at IS NULL` 判"已推"）；回收函数 `retract_stale_synthetic_from_ssll` 的候选集在 `:292` 写死 `.in_("tier",["爆","大爆"])`，共用判据 `metric_tier_untrustworthy_reason()` 第一句 `:253` 又是 `if row.get("tier") not in ("爆","大爆"): return None`——**两道独立的 tier 门**，降档行连候选集都进不去。脚本 `:168-171` 自己写着"一旦推过去…再改 mapping 也追不回来"。

### 影响多少

| 项 | 数 | 证据 |
|---|---|---|
| 已推 ssll 但 tier 已不是 爆/大爆/参考 | **285 行**（趴230 · 风控54 · 预备1） | SQL 今日实查 |
| 占 ssll 池 TV 来源样本 | **285 / 597 ≈ 48%** | join `public.reference_samples`（同一 project，可读），285 条样本全部还在，`ai_analysis._truth_vault_tier` 仍是 爆244/大爆41，`quality_score` 100/200 |
| 这 285 行能被现有自愈路径捞回的 | **0 行** | `synthetic=true` 0 条、含 `comment_maintained_routes` 0 条 |
| 历史真降档 note | **330 个 / 368 次**（2026-06-01 → 今日） | `truth_vault.audit_log` |
| 被风控/疑似限流顶掉的 | **4 行**（3 行已进飞轮+书架+ssll） | `_tier_source_raw like '%风控%' and tier is distinct from '风控'` |

**注意 285 行里 284 行集中在 2026-08-19 一次性发生（全 OKMAN）**——所以今天这不是"每天在漏"，是"一次大规模降档留了 284 条没人收"。但这恰恰是论据：那还是运营手写 tier 的时代。文档把 `流量状态` 交给机器每轮重算之后，降档从偶发变成常态。

### 不处理会怎样

写作引擎的仿写样本池（`public.reference_samples`，另一个 Supabase）里近一半 TV 注入样本是过期档位，而且**只会涨不会跌**——每一次机器把某行从爆改成趴/风控，都是一次永久泄漏。书架那边不用担心（`v_flywheel_lesson_cards` 是对 notes 的实时视图，`schemas/notes_v1_14_shelf_ticket_gate.sql:30-56`，tier 一掉当场出架，实测 330 条降档 note 里 99 条有卡、97 条已自动下架），**问题只在 ssll 这一条跨库单向门**。

### 最小处理（三步，都不需要监控系统配合）

1. **只读断言先上**（零风险，当晚就有基线）：
   `select count(*) from truth_vault.notes where synced_to_ssll_at is not null and (tier not in ('爆','大爆','参考') or tier is null)` → 今天基线 **285**，涨了就红。
2. **`scripts/_common.py:453` 给风控否决位**：任一 token 判成 `风控` → 直接返回 `风控`，不进 `max` 择优。理由：风控说的是"这条还能不能看"，与"它有多火"不同维，且这正是文档"风控中不可覆盖"的语义。影响全 17 项目（今天只改变 4 行的结果），配一条 CI 断言（`ci.yml` 现在对"风控"零命中）。
3. **`sync_truth_vault_baokuan_to_sanshengliubu.py:292` + `:253` 两处一起放宽**：候选集从 `.in_("tier",["爆","大爆"])` 改成 `synced_to_ssll_at IS NOT NULL`，判据加一路"tier 已跌出 爆/大爆/参考 → 撤回"。删除走既有的 `:317` delete 路径（D-068 那 41 条就是这么删的，机制现成）。**先 dry-run 出 285 行名单给 ssll 那边过目**——这一步是跨仓，见第 6 节。

只改 `:292` 不改 `:253` 是**无效的**，两道 tier 门必须一起动。

## 4. 机会清单：这张表白送了什么

TV 现在有的全部指标能力 = notes 上 5 个**标量快照列**（impressions / reads / interactions / comments_count / hit_blue_keywords），每晚 upsert 覆盖。没有事件时刻、没有方向、没有观众。这张表一次性送来四个新维度。

### 4.1 评论时序 / 速度 —— TV 完全没有的维度

**容器已经存在，而且已经在写。** `truth_vault.metric_snapshots` 17 列：`collected_at` / `window_label` / `hours_since_publish` + 同一套指标，其中 `comments_count` 已有 **1758 行**非空、`hit_blue_keywords` 1493 行。扇出代码 `sync:973`。所以这不是"建时序表"，是"改 window 语义"——成本低一个数量级。

**但现在还不是时序，原因是冷启动不是设计缺陷。** 1339 个有 cc 的 note 里 931 个只有 1 个点，408 个 ≥2 点、其中 43 个两次值不同。关键在分层：**按首读贴龄拆，<72h 首读的 31 个 note 里 24 个在涨（77.4%）**，72-240h 的 5.9%，>30d 的 **0%**；有 3 个快照的 11 个 note **全部在涨**。`comments_count` 进快照是 2026-09-17 才开始的（5 个采集日，1195/1339 是 09-22 一晚扫进来的）。**不是"零斜率"，是"抓到时太老"——新表新贴会自己变好。**
