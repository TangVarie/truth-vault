# 信号定义与标签污染实测（2026-09-16）

## 为什么存在

owner 2026-09-16：

> 我觉得我们需要把目前每个项目的 mapping 再细化一下，这里面有些比较关键的地方需要明确一下信号和定义。
> 举个例子，一篇帖子可能标记为爆贴，但其背后的原因是评论数过了 50，但这有可能是我们刷的，所以其真实的流量一般般；
> 又比如，有些帖子我们判断还不错，我们去投了流量，但是投流之后有些涨的可以，说明这个帖子是有潜力的……
> 诸如此类，如果不确定好的话，信号太杂乱了

这份文档把「杂乱」摊开量化。**结论：373 个爆款里 79 个（21%）的标签是被污染的**，
其中只有 10 个（伪爆贴）已经被现有的闸拦住。

> 这不是 mapping 列名写得细不细的问题。是**同一个词「爆」在库里指着四五种不同的东西**。

---

## 一、四类信号，四种处理原则

| 类 | 是什么 | 能当标签吗 | 能当特征吗 |
|---|---|---|---|
| **结果类** | tier / impressions / reads / interactions | ✅ 这就是标签 | ❌ 发布前拿不到 |
| **内容类** | raw_content / emotional_lever / archetype / audience / format | ❌ | ✅ 发布前就有，无泄漏 |
| **干预类** | 控评 / 铺评 / 置顶 / 改评 / 投流 | ❌ | ⚠️ **多数是后验泄漏** |
| **运维类** | 巡查状态 / 最近检查时间 / 排队刷新 / 连续失败次数 | ❌ | ❌ 纯机器人工单 |

**干预类是最危险的一类** —— 它看起来像特征（发布后就有值），实际是结果的后果。
喂给模型会让 AUC 虚高，上线后一文不值。

## 二、逐信号定性

### ① 标签来源：`tier` 的五种来路，可信度完全不同

`tier_source` 已经记了来路，但下游（包括我自己 9/15 的 L2 分析）普遍直接读 `tier` 忽略它。

| tier_source | 行数 | 含义 | 可信度 |
|---|---|---|---|
| 状态字段 | 5,384 | 运营在「流量状态」列手标 | 高（但口径见 ③） |
| 数值推断 | 43 | **运营没标，脚本按阈值自己升的** | 低 |
| 数据异常 | 1 | — | — |
| null | 521 | 没有 tier 源 | — |

**43 条数值推断里 41 条是爆/大爆。** 这些行运营写的是「评估中」——
即「还没下结论」，脚本把它升成了「爆」。RIO 3 / TUGE 4 / WTG 3 / XIWU 2 等。

→ **口径：L2 训练集必须排除 `tier_source='数值推断'`。** 运营没判的不算判了。

### ② 假爆款闸：`data_quality_flags.synthetic` —— 已存在，但只认两个信号

现有实现（`_SYNTHETIC_TIER_SRC_RE`）认：
- 笔记状态含「关注」（WTG 式）
- tier 源命中 `伪爆[贴帖]|伪\d+评`（RIO 式「伪爆贴500」、BJS/SPX 式「伪爆帖500」）

**这部分工作得很好**：库里「标了伪爆但没标 synthetic」= **0 条**。看板 `v_dash_*` 也已经把它们剔出爆款率。

但它的视野只有这两个信号。爆款里：

| | 条数 | synthetic 认吗 |
|---|---|---|
| 运营手标伪爆贴 | 10 | ✅ 全部拦住 |
| 挂了「维护评论50条」 | 26 | ❌ |
| 纯数值推断升上来的 | 41 | ❌ |
| 互动量 ≤ 本项目「趴」中位数 | 9 | ❌ |
| synthetic 从没被判定过（两个信号都不在场） | 212 | ⚠️ 键都没写 |

### ③ 「爆」的口径在各项目之间不可比

各项目「爆」的互动量中位数：

| 项目 | 爆的中位互动 | 趴的中位互动 |
|---|---|---|
| TGV | 925 | — |
| NRT_2 / NRT_3 | 589 / 526 | 3 / 4 |
| RIO / OKMAN | 466 / 449 | 2 / 4 |
| NUC | 294 | 4 |
| SPX / TUGE | 80 / 52 | 2 / 3 |
| WTG / BJS | 36 / 13 | 1 / 0 |
| **ANSHEN** | **1** | 1 |

**ANSHEN 的「爆」（中位互动 1）比 NUC 的「趴」（中位 4）还差。**

→ **口径：分数、阈值、爆款率永远不能跨项目比。** 只能项目内排序。

### ④ 刷评：`维护评论50条` —— owner 那个例子的实证

TUGE 的这一列里存的是**50 条水军评论的完整文案**（一整段，不是计数）。

| TUGE 爆贴 | 条数 | 互动量中位数 |
|---|---|---|
| 挂了「维护评论50条」 | 26 | **1 / 2 / 3 / 6 / 13** |
| 没挂 | 12 | **156** |

同期 TUGE 的「实时数据.评论数」中位 **48**（卡在 50 门槛下沿），而互动量中位 **6**。
评论和互动彻底脱节 —— **评论是铺的，互动是真的**。

### ⑤ 控评：真爆贴也会控评，不能一刀切

tier 源里出现过：`控评✅`（RIO 9）、`控评&置顶✅`（SPX 2）、`重点控评`（TUGE 1）、`注意控评`（SPX 1）。

RIO 的 9 条控评里 8 条同时是「伪爆贴500」，但 **SPX 的「控评&置顶✅」挂在互动量 136 的真大爆上**。

→ **口径：控评 ≠ 假爆款。** 把控评一律判 synthetic 等于把真赢家删出飞轮。
必须**正交另开一个标记**。这就是 D-060 `comment_maintained` 的由来。

### ⑥ 后验泄漏：`评论状态`

| 评论状态 | n | 其中爆 | 互动中位 |
|---|---|---|---|
| 改评发布 | 24 | **20 (83%)** | **512** |
| 二次评论 | 5 | **5 (100%)** | **362** |
| 改评显示 | 1 | 1 | 1225 |
| 正常发布 | 427 | 88 | 8 |
| 显示评论 | 942 | 66 | 5 |
| 没有显示 | 2,069 | 90 | 3 |

**「改评发布」「二次评论」几乎 100% 命中爆贴** —— 因为只有帖子已经起量，运营才会回去改评/二次铺评。

→ **口径：这三个值是果不是因。标出来是为了让下游主动排除，不是为了当特征。**
把它喂进 L2，AUC 会好看得离谱，上线归零。

### ⑦ 实时 vs 累计：`实时数据.评论数` / `上次评论数`

巡查机器人写的快照对。分布：

| 项目 | 有实时值 | 涨了 | 没动 | 掉了 | 实时评论中位 | 互动中位 |
|---|---|---|---|---|---|---|
| TUGE | 80 | 19 | 56 | 3 | **48** | 6 |
| SPX | 458 | 0 | 29 | 0 | 2 | 2 |
| ANSHEN | 177 | 5 | 172 | 0 | 0 | 1 |
| BJS | 180 | 3 | 177 | 0 | 0 | 0 |

owner 说的「有可能是新刷的也有可能是新涨起来的」—— **只看单次快照区分不了**。
能区分的是差分（实时 − 上次）+ 它和互动量的比值：**评论涨了但互动没涨 = 刷**。
目前只有 TUGE 有 22 条发生过变化，样本太少，先把信号留痕，不下判定。

## 三、缺失的信号：**投流数据全库不存在**

owner 提的第二个场景：

> 有些帖子我们判断还不错，我们去投了流量，投流之后有些涨的可以，说明这个帖子是有潜力的，
> 之前只是种种原因被限制了；有些投不出来，说明确实帖子质量就是差

全库 5,949 行、所有 raw_extra 键扫过一遍，匹配 `投流|薯条|加热|推广|助推|千川|付费|投放|dou`：

| 沾边的列 | 行数 |
|---|---|
| 起量时间 | 48 |
| 起量情况 | 29 |
| **投流相关列** | **0** |

**这个维度飞书表里就没有。** 不是 mapping 没接，是运营根本没在记。

这也是所有信号里**信息量最大的一个** —— 它能把「内容差」和「内容好但没投出去」分开，
而这正是现在 AUC 卡在 0.6 的核心原因之一：模型看不到「这条根本没获得曝光机会」。

→ **需要运营侧新增**，见第五节。

## 四、已证伪的两个担心（别再查了）

### ① 「副本」列 ≠ 另一份数据

`互动副本`/`阅读副本`/`曝光副本`/`互动量副本`… 共 8 个项目 3,268 行。
与主值逐行比对：**3,260 行完全相等**，7 行不等（全在 RIO），1 行只有副本。

→ **纯复制列，永久忽略。**

### ② 「同一份文案铺多个账号」不是 SPX 反常的原因

我一开始猜 SPX 正文模型反向（AUC 0.232）是因为素人分发导致同文案不同结果。查下来不成立：

| 项目 | 文案重复率 | 正文模型 AUC |
|---|---|---|
| RIO | **27.8%** | 0.626（好） |
| SPX | **3.9%** | **0.320（反向）** |
| 其余 13 个 | ≈0% | — |

重复率最高的 RIO 正文模型反而是好的。SPX 的真实原因是**正文长度**：
SPX 的爆贴正文中位 **118 字**，趴贴 **253 字** —— 爆的比趴的短一半。
其它项目没有这个规律，跨项目学来的权重在 SPX 上系统性反向。

## 六、代码侧已经改了什么

**D-060 `data_quality_flags.comment_maintained`**（本次）—— 与 `synthetic` **正交**的新标记。

为什么不并进 `synthetic`：见 ⑤。`synthetic` 被 20 多处读（看板 `v_dash_*`、飞轮通道 1 ssll、
馆员、ssll 回灌），语义一动全身动，而且并进去会误删真赢家。

三路信号任一成立即为 true：
1. tier 源含「控评」
2. 工单列 `维护评论50条` / `评论铺设情况` 非空
3. `评论状态` 含 `改评发布` / `二次评论` / `改评显示`（后验干预值）

**三路都不在场时缺键，不写 false** —— 一张表没有控评列，不等于它的帖子没被控评。
写 false 是拿「假阴性」冒充「已核实」。缺键让下游能区分「没被控评」和「不知道」。

未声明列（D-055 `_undeclared`）路径同样要认 —— BJS/SPX 的「评论状态」就是未声明的，
不走这条路会导致同一个运营动作因为「这张表声明没声明」而时有时无。

守卫：CI 第 ⑦ 组 7 个用例，5 处反证全部变红。

## 七、复现 SQL

### 标签污染盘点

```sql
WITH pa AS (
  SELECT project_id, percentile_disc(0.5) WITHIN GROUP (ORDER BY interactions) pm
  FROM truth_vault.notes WHERE tier='趴' AND interactions IS NOT NULL GROUP BY 1
), b AS (
  SELECT n.*, pa.pm, (n.data_quality_flags->>'synthetic')::bool syn
  FROM truth_vault.notes n LEFT JOIN pa USING (project_id) WHERE n.tier IN ('爆','大爆')
)
SELECT count(*) 爆款总数,
  count(*) FILTER (WHERE syn IS TRUE) 已标synthetic,
  count(*) FILTER (WHERE syn IS NULL) 从没判定过,
  count(*) FILTER (WHERE COALESCE(raw_extra->>'_tier_source_raw','') LIKE '%伪爆%' AND syn IS NOT TRUE) 伪爆漏标,
  count(*) FILTER (WHERE (raw_extra ? '维护评论50条') AND syn IS NOT TRUE) 刷50评没标,
  count(*) FILTER (WHERE tier_source='数值推断' AND syn IS NOT TRUE) 数值推断没标,
  count(*) FILTER (WHERE interactions<=pm AND syn IS NOT TRUE) 低于趴中位没标
FROM b;
```

### 各项目「爆」的口径

```sql
SELECT project_id,
  percentile_disc(0.5) WITHIN GROUP (ORDER BY interactions)
    FILTER (WHERE tier IN ('爆','大爆')) 爆的中位互动,
  percentile_disc(0.5) WITHIN GROUP (ORDER BY interactions)
    FILTER (WHERE tier='趴') 趴的中位互动
FROM truth_vault.notes WHERE interactions IS NOT NULL
GROUP BY 1 HAVING count(*) FILTER (WHERE tier IN ('爆','大爆')) > 0
ORDER BY 2 DESC NULLS LAST;
```

### 后验泄漏字段

```sql
SELECT left(COALESCE(raw_extra->>'评论状态', raw_extra->'_undeclared'->>'评论状态'),20) 评论状态,
       count(*) n, count(*) FILTER (WHERE tier IN ('爆','大爆')) 其中爆,
       percentile_disc(0.5) WITHIN GROUP (ORDER BY interactions) 互动中位
FROM truth_vault.notes
WHERE COALESCE(raw_extra->>'评论状态', raw_extra->'_undeclared'->>'评论状态') IS NOT NULL
GROUP BY 1 ORDER BY n DESC;
```

### 全库找某类信号在不在

```sql
SELECT k, count(*) n, string_agg(DISTINCT project_id, ',') projs
FROM truth_vault.notes, jsonb_object_keys(COALESCE(raw_extra,'{}'::jsonb)) k
WHERE k ~ '投流|薯条|加热|推广|助推|千川|付费|投放'   -- 换成你要找的信号
GROUP BY 1 ORDER BY n DESC;
```

## 八、L2 训练集的口径（结论）

基于以上，L2 的正例定义应当是：

```sql
tier IN ('爆','大爆')
AND tier_source <> '数值推断'                                    -- ① 运营没判的不算
AND COALESCE(data_quality_flags->>'synthetic','false') <> 'true'  -- ② 已有的假爆款闸
AND COALESCE(raw_extra->>'_tier_source_raw','') NOT LIKE '%伪爆%' -- ③ ②的冗余兜底
AND NOT (raw_extra ? '维护评论50条')                              -- ④ 刷评
AND interactions > (本项目 '趴' 的互动中位数)                      -- ⑤ 内部自洽
```

按这个口径：**373 → 294 个正例**。
留一项目交叉验证 AUC 从 0.612（污染标签）变成 **0.624**（清洗后）。

**AUC 只涨了 0.012，但那 0.012 不是重点** —— 重点是之前每 5 个正例里有 1 个是假的，
任何基于它的判断都在被误导。详见 [l2-feasibility.md](l2-feasibility.md)。
